# 작업 마무리하기

여기까지 온 작업을 팀에 넘기는 절차다. 재환·위진이 순서를 외우지 않아도 되도록
**정리부터 카톡 문장까지 이 스킬 하나가 다 챙긴다.**

순서를 바꾸지 않는다. 특히 정리(2단계)는 저장 지점(5단계)보다 **반드시 먼저** 한다.
저장한 뒤에 정리하면 저장 기록이 지저분해지고, 리뷰하는 규민이 무엇이 진짜 변경인지
가려내야 한다.

---

## 0. 지금 어디에 있는지 확인

현재 복사본 이름과 바뀐 파일 목록을 확인한다.

- **`main` 이면 여기서 멈춘다.** 올릴 작업이 복사본에 없다는 뜻이다.
  사용자에게 `/new-work <하려는 작업 한 줄 설명>` 을 치라고 안내하고 끝낸다.
- **바뀐 파일이 하나도 없고 올릴 저장 지점도 없으면** 멈춘다.
  고친 게 없는데 마무리할 것도 없다고 알린다.

## 1. 정말 다 됐는지 확인한다 (안전망)

`new-work` 에서 이미 되물었다면 여기서는 한 번만 짚고 넘어간다.
**`/pr` 을 곧바로 친 경우**에는 이 단계가 유일한 확인 지점이므로 제대로 묻는다.

바뀐 파일 목록을 보여주고, 무엇을 하려던 작업이었는지 확인한다.
복사본 이름(`feat/comment-delete-button` 등)이 단서가 된다.

> 올리기 전에 확인할게요. 이번에 고친 파일은 이렇습니다:
> - `components/CommentForm.tsx`
>
> 브라우저 화면에서 원하는 대로 동작하는 것까지 확인하셨나요?
> 아직이면 지금 확인해 주세요. 올리고 나면 팀 전체가 보게 됩니다.

**사용자가 확인했다고 답하기 전에는 다음으로 넘어가지 않는다.**

## 2. 코드 정리 (simplify)

`simplify` 스킬을 실행한다. 클로드 코드에 기본으로 들어 있는 스킬이라
따로 설치할 것이 없다.

정리가 끝나면 **무엇이 어떻게 바뀌었는지 사용자에게 보여주고 확인받는다.**
개발이 처음인 사람은 자기가 쓴 코드가 소리 없이 바뀌면, 다음에 그 파일을 열었을 때
자기 코드가 아닌 것 같아 당황한다.

> 코드를 정리했습니다. 이렇게 바뀌었어요:
> - 같은 내용을 두 번 쓴 부분을 하나로 합쳤습니다
> - 안 쓰는 변수 하나를 지웠습니다
>
> 동작은 그대로입니다. 브라우저 화면 한 번만 다시 봐주세요.

정리한 뒤에는 **화면이 여전히 정상인지 확인하도록 안내한다.**
정리가 동작을 바꾸는 일은 드물지만, 확인하는 습관이 더 중요하다.

## 3. 검사

`package.json` 의 `scripts` 를 보고 **있는 것만** 실행한다.
없는 프로젝트에서는 조용히 넘어간다. 보통 `typecheck` 와 `lint` 다.

**실패하면 멈춘다.** 실패한 내용을 한국어로 풀어서 설명하고, 고친 뒤 다시 검사한다.
검사를 통과하지 못한 코드를 올리지 않는다. 기계가 잡아낼 수 있는 문제에
규민의 리뷰 시간을 쓰게 하지 않는다.

## 4. 무엇을 올릴지 사용자와 맞춘다

저장 지점에 붙일 메시지를 짓고, **사용자에게 보여준 뒤 확인받는다.**

형식:

```
<종류>: <무엇을 했는지 한글 한 줄>

(선택) 왜 그렇게 했는지
```

종류는 `feat`(기능 추가), `fix`(버그 수정), `docs`(문서), `style`(디자인/서식),
`refactor`(동작 그대로 정리), `chore`(설정) 중 하나. 복사본 이름의 앞부분과 맞춘다.

## 5. 저장 지점을 만들고 GitHub에 올린다

담기 → 저장 지점 만들기 → 올리기 순서로 진행한다.

- **고친 파일을 이름으로 적어서 담는다.** 전체를 한꺼번에 담으면 의도하지 않은
  파일이 딸려간다.
- **`.env` 로 시작하는 파일은 절대 담지 않는다.** 비밀번호와 열쇠가 들어 있다.
  목록에 보이면 그 자리에서 멈추고 사용자에게 알린다.
- 올릴 때는 지금 복사본 이름을 그대로 쓴다.

## 6. 합쳐달라고 요청한다 (PR)

`gh` 명령이 깔려 있는지 먼저 확인한다.

**`gh` 가 있으면** — 제목과 본문으로 요청을 만든다. 본문은 파일로 넘겨야
한글이 깨지지 않는다.

**`gh` 가 없으면** — 올리고 나면 터미널에 요청 만드는 주소가 나온다.
그 주소와 함께 **붙여넣을 제목과 본문을 만들어서 준다.**
사용자는 주소를 열고 복사해서 붙이기만 하면 된다.

본문에는 이 네 가지를 넣는다:

- **무엇을 바꿨나** — 화면에서 무엇이 달라지는지. 코드 이야기가 아니라 눈에 보이는 변화
- **왜** — 이 작업을 한 이유
- **확인한 것** — 브라우저에서 확인한 내용, 검사 통과 여부
- **DB 변경 여부** — `db/schema.sql` 을 건드렸으면 "DB 변경 필요"라고 크게 적는다

## 7. 규민에게 보낼 카톡 문장을 만든다

주소만 던지면 규민이 열어봐야 무슨 작업인지 안다. **한 줄 요약을 같이 준다.**
사용자가 그대로 복사해서 카톡방에 붙일 수 있는 형태로 만든다.

> 다 됐습니다. 아래를 그대로 복사해서 카톡방에 붙여넣으세요.
>
> ```
> 댓글 삭제 버튼 만들었어. 리뷰 부탁해!
> https://github.com/Baegyum/idea-vote-app/pull/7
> (CommentForm.tsx 한 파일, 검사 통과, DB 변경 없음)
> ```

## 8. 다음에 무엇이 일어나는지 알려준다

여기서 사용자를 놓아두지 않는다. **기다리는 동안 뭘 하면 되는지**까지 말해준다.

> 이제 규민님이 확인하고 합쳐줄 때까지 기다리시면 됩니다.
> 합쳐졌다는 연락을 받으면 `/close-work` 를 쳐주세요. 뒷정리를 해드릴게요.
>
> 기다리는 동안 다른 작업을 시작하셔도 됩니다. 그때는 `/new-work` 부터요.

---

## 하지 않을 것

- **합치지 않는다.** 합치는 것은 규민이 GitHub 웹에서만 한다. 예외 없다.
- **검사에 실패한 채로 올리지 않는다.**
- **사용자 확인 없이 저장 지점 메시지를 정해서 그냥 진행하지 않는다.**
- **`main` 에서 이 스킬을 진행하지 않는다.** `/new-work` 로 돌려보낸다.
- `.env` 로 시작하는 파일을 저장 지점에 담지 않는다.

## 말투 규칙

재환·위진은 개발이 처음이다. 팀 문서(`docs/01-git-기초.md`)의 말을 그대로 쓴다.

| 이 말을 쓴다 | 이 말은 피한다 |
|---|---|
| 내 복사본 | 브랜치 (처음 나올 때만 괄호로 병기) |
| 저장 지점 만들기 | 커밋 |
| GitHub에 올리기 | 푸시 |
| 합쳐달라고 요청하기 | PR 생성 (약어는 괄호로 병기) |

명령어를 알려줄 때는 **한 번에 하나만**, 왜 필요한지 한 줄 설명을 붙인다.
