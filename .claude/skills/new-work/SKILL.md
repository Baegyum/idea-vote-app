# 새 작업 시작하기 — 내 복사본 만들기

`main` 에서 바로 작업하면 팀 전체가 위험해진다. 그래서 작업 하나마다
"내 복사본"을 만들고 그 안에서만 고친다.

**이 스킬은 두 단계로 동작한다.** 지금 어느 단계인지 먼저 판단한다.

- 한 줄 설명 **없이** 열렸다 → 단계 A (안내만 하고 멈춤)
- 한 줄 설명과 **함께** 열렸다 → 단계 B (절차 수행)

---

## 단계 A — 설명 없이 열렸을 때: 안내만 한다

사용자가 "댓글 기능 만들래" 처럼 자연스럽게 말해서 이 스킬이 열린 경우다.

**절대 브랜치를 만들지 않는다. 상태 확인도 하지 않는다.** 사용자가 직접
명령을 치도록 안내하고 거기서 멈춘다.

왜 한 번 더 치게 하는가:
- 사용자가 자기 작업을 **한 줄로 스스로 정의하게** 된다. 뭘 만들 건지 흐릿한 채로 시작하는 걸 막는다
- 그 한 줄이 **브랜치 이름의 근거이자, 이미 있는 기능을 찾는 검색어**가 된다
- 복사본이 만들어지는 순간을 사용자가 **의도적으로** 겪게 된다. 자기도 모르게 만들어지면 배우지 못한다

안내는 이렇게 한다. 사용자가 말한 내용을 그대로 넣어서 **복사해서 바로 칠 수 있는 형태**로 준다.

> 좋아요. 그 작업을 시작하려면 아래를 쳐주세요.
>
> `/new-work 댓글 기능 추가`
>
> 뒤에 뭘 할 건지 한 줄로 적으시면 됩니다. 그러면 제가 이미 비슷한 게 있는지
> 찾아보고, 위진님 전용 복사본을 만들어 드릴게요.

명령어 한 줄만 주고 멈춘다. 다른 설명을 길게 붙이지 않는다.

---

## 단계 B — 설명과 함께 열렸을 때: 절차를 수행한다

### 1. 지금 상태 확인

```
git status --porcelain
git branch --show-current
```

- **저장 안 된 변경이 있으면 먼저 멈춘다.** 무엇이 바뀌었는지 보여주고,
  지금 자리에서 저장할지 / 새 복사본으로 가져갈지 물어본다. 임의로 버리지 않는다.
- 이미 `main` 이 아닌 곳에 있으면, 하던 작업이 끝났는지 확인한다.
  안 끝났으면 새로 만들지 말고 하던 걸 계속하라고 안내한다.

### 2. main 을 최신으로

```
git checkout main
```
```
git pull --ff-only origin main
```

이걸 빠뜨리는 게 **초보자 사고 1위**다. 어제 누군가 합친 코드를 모른 채
옛날 코드 위에서 작업하면, 나중에 합칠 때 충돌이 난다.

`--ff-only` 는 "깔끔하게 이어붙일 수 있을 때만 받아라"는 뜻이다.
꼬인 상태를 조용히 만들지 않고, 문제가 있으면 그 자리에서 멈춘다.

**반드시 3단계보다 먼저 한다.** 옛날 코드에서 찾으면 이미 있는 기능을 못 보고 지나친다.

### 3. 이미 있는 기능인지 찾아본다

받은 한 줄 설명에서 핵심 낱말을 뽑아 코드베이스를 찾는다. 화면, 컴포넌트,
API 경로, DB 테이블을 **함께** 본다. 한 군데만 보면 놓친다.

예: "댓글 기능 추가" → `comment` 로 `components/`, `app/api/`, `db/schema.sql` 을 훑는다.

**이미 있으면** — 무엇이 어디에 있는지 보여주고 물어본다.

> 찾아보니 댓글 기능이 이미 있네요:
> - `components/CommentForm.tsx` — 댓글 입력 폼
> - `app/api/ideas/[id]/comments/route.ts` — 댓글 저장
> - `db/schema.sql` 의 `comments` 테이블
>
> 셋 중 어느 쪽일까요?
> 1. 지금 있는 것에 **없는 기능을 더한다** (예: 댓글 삭제 버튼)
> 2. 있는데 **잘못 동작해서 고친다**
> 3. 이건 다른 기능이다 (제가 잘못 찾았습니다)

**없으면** — 새로 만드는 것으로 진행하되, 찾아봤다는 사실을 한 줄 알린다.

> `comment` 로 찾아봤는데 없네요. 새로 만드는 것으로 진행할게요.

이 단계를 넣은 이유: 초보자가 **이미 있는 기능을 처음부터 다시 만드느라
반나절을 쓰는 일**이 실제로 흔하다. 코드를 열어보기 전에는 알 수가 없다.

### 4. 종류와 이름 정하기

3단계 결과에 따라 종류가 갈린다.

| 종류 | 언제 | 3단계에서 |
|---|---|---|
| `feat/` | 없던 걸 새로 만든다 | 못 찾았음, 또는 있는 것에 기능을 더함 |
| `fix/` | 있는데 잘못 동작한다 | 찾았고 사용자가 "고장났다"고 함 |
| `docs/` | 문서만 고친다 | — |
| `chore/` | 설정, 정리 | — |

**이름은 영어 소문자와 하이픈만.** 한글이나 띄어쓰기가 들어가면 다른 사람
컴퓨터에서 깨진다. 한 줄 설명을 영어로 옮겨서 제안하고, **확인받은 뒤에** 만든다.

예: `/new-work 댓글 삭제 버튼 추가` → `feat/comment-delete-button`

### 5. 복사본 만들기

```
git checkout -b <정한-이름>
```

### 6. 개발 서버를 켜고 화면을 띄운다

`package.json` 에 `dev` 스크립트가 있는 프로젝트라면 **이 단계를 건너뛰지 않는다.**
개발이 처음인 사람은 코드만 고쳐서는 무엇이 달라졌는지 알 수 없다.
화면을 보면서 고쳐야 배운다.

- 터미널에서 직접 서버를 띄우지 말고, **클로드 코드에 내장된 브라우저 창**에 띄운다
- `.claude/launch.json` 의 설정을 쓴다. 없으면 만든다
- 띄운 뒤 화면이 제대로 나오는지 한 번 확인하고 사용자에게 보여준다

띄웠으면 아래 세 가지를 **반드시** 말해준다. 하나도 빠뜨리지 않는다.

**① 주소가 무엇인지**

> 개발 서버를 켜서 오른쪽 브라우저에 띄웠습니다. 주소는 `http://localhost:3000` 입니다.

**② 이건 개발 전용이고 안전하다**

> `localhost` 는 "내 컴퓨터"라는 뜻입니다. 여기 보이는 화면은 위진님 컴퓨터
> 안에서만 돌아가는 **개발 전용 연습 화면**이라, 여기서 무엇을 하든 팀원들이나
> 실제 사이트에는 아무 영향이 없습니다. 마음껏 눌러보고 망가뜨려도 됩니다.
> 인터넷에 올라간 진짜 사이트는 따로 있습니다.

**③ 작업하는 동안 이 화면을 계속 보라**

> 이제부터 코드를 고치면 이 화면이 몇 초 안에 저절로 바뀝니다.
> **고칠 때마다 이 화면을 확인하세요.** 원하는 대로 바뀌고 있는지 눈으로 보는 게
> 지금 단계에서 가장 중요합니다. 이상하면 바로 말씀해 주세요.

포트를 이미 **다른 폴더의 프로젝트가 쓰고 있으면 그 사실을 먼저 알린다.**
엉뚱한 앱 화면을 보면서 "왜 안 바뀌지" 하고 헤매는 사고가 실제로 있었다.

### 7. 어디에 있는지 알려주고, 작업으로 넘어간다

초보자에게 가장 헷갈리는 건 "지금 내가 어디 있는가"다. 반드시 알려준다.

- 지금 어느 복사본 안에 있는지
- 여기서 무엇을 고쳐도 `main`(인터넷에 올라가 있는 진짜 코드)은 안전하다는 것

그 다음 **3단계에서 찾은 내용을 근거로 실제 작업을 시작한다.** 어디를 고쳐야
하는지 이미 알고 있으므로, 파일부터 다시 찾지 말고 이어서 진행한다.

**작업하는 동안 먼저 PR 이야기를 꺼내지 않는다.** 이건 중요한 금지 사항이다.
"이제 PR 만들까요?" 라고 물으면 개발이 처음인 사람은 그것을 **"다 됐다는 신호"**
로 받아들인다. 실제로는 절반만 된 상태일 수 있는데도 그렇다.
사용자가 스스로 "다 됐어" 라고 말할 때까지 기다린다.

### 8. 사용자가 "다 됐어" 라고 하면: 되묻고 나서 넘긴다

여기서 바로 마무리로 넘어가지 않는다. **한 번 되묻는다.**

되묻는 근거는 **처음에 받은 한 줄 설명**이다. 막연히 "다 되셨어요?" 라고 묻지
말고, 그 한 줄에 적힌 것이 실제로 되는지 **구체적으로** 짚는다.

예: `/new-work 댓글 삭제 버튼 추가` 로 시작했다면

> 마무리하기 전에 하나만 확인할게요. 처음에 "댓글 삭제 버튼 추가"로 시작하셨는데,
> 브라우저 화면에서 이것까지 확인해 보셨나요?
>
> - 삭제 버튼이 화면에 보이는지
> - 눌렀을 때 댓글이 실제로 사라지는지
> - 새로고침해도 사라진 채로 있는지
>
> 아직 안 해보셨으면 지금 눌러보세요. 다 되면 알려주세요.

확인할 항목은 **작업 내용에 맞게 그때그때 만든다.** 위는 예시일 뿐이다.
화면에서 눈으로 확인할 수 있는 것을 우선으로 넣는다.

사용자가 "확인했다"고 하면, 그때 마무리 명령을 안내한다. 여기서도 직접
저장·올리기를 하지 말고, **사용자가 치게 한다.**

> 확인되셨네요. 그럼 마무리하겠습니다. 아래를 쳐주세요.
>
> `/pr`
>
> 코드 정리부터 규민님께 보낼 카톡 문장까지 한 번에 해드릴게요.

## 말투 규칙

재환·위진은 개발이 처음이다. 팀 문서(`docs/01-git-기초.md`)의 말을 그대로 쓴다.

| 이 말을 쓴다 | 이 말은 피한다 |
|---|---|
| 내 복사본 | 브랜치 (처음 나올 때만 괄호로 병기) |
| 저장 지점 만들기 | 커밋 |
| GitHub에 올리기 | 푸시 |
| 합쳐달라고 요청하기 | PR 생성 (약어는 괄호로 병기) |

명령어는 **한 번에 하나만**, 왜 필요한지 한 줄 설명을 붙인다.

## 하지 않을 것

- **단계 A에서 브랜치를 만들지 않는다.** 안내하고 멈추는 것이 이 단계의 전부다.
- **복사본만 만들고, 저장 지점까지 대신 만들지 않는다.** 무엇을 고칠지는 사용자가 정한다.
- `main` 에서 차단됐다는 이유만으로 사용자 확인 없이 이름을 지어 만들지 않는다.
- **작업 중에 먼저 PR 을 제안하지 않는다.** 사용자가 끝났다고 말하는 것이 먼저다.
- 개발 서버를 켜고 나서 주소만 던지지 않는다. 위 ①②③ 을 모두 말한다.
