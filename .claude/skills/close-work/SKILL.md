# 작업 마무리 뒷정리

규민이 합친 뒤에 하는 정리다. **팀 세 명 모두가 치는 명령이다.**

| 누가 치는가 | 정리할 것 |
|---|---|
| 작업을 올린 사람 | 다 쓴 내 복사본 삭제 + 최신 코드 받기 |
| 나머지 사람들 | 최신 코드 받기 (복사본은 없음) |

**정리할 게 없어도 정상이다.** 남이 올린 작업이 합쳐지면 내 컴퓨터의 `main` 도
낡는다. 그 상태로 다음 작업을 시작하는 것이 **초보자 사고 1위**이므로,
합쳐졌다는 연락을 받으면 셋 다 이 명령을 치는 것이 맞다.

---

## 0. 지금 상태 확인

현재 복사본 이름과 저장 안 된 변경이 있는지 본다.

**저장 안 된 변경이 있으면 여기서 멈춘다.** 정리하는 도중에 날아갈 수 있다.
무엇이 바뀌었는지 보여주고 물어본다.

> 정리하기 전에, 아직 저장하지 않은 변경이 있어요:
> - `components/CommentForm.tsx`
>
> 이건 어떻게 할까요?
> 1. 이것도 마무리해서 올린다 → `/pr` 을 쳐주세요
> 2. 필요 없는 거라 버린다 → 버려도 되는지 확실하면 말씀해 주세요
>
> 확실하지 않으면 규민님께 먼저 물어보세요. 지운 건 되돌릴 수 없습니다.

## 1. 최신 정보 받아오기

```
git fetch --prune origin
```

`--prune` 이 중요하다. 합쳐지면 GitHub 쪽 복사본은 자동으로 지워지도록
설정돼 있는데, 내 컴퓨터에는 **"GitHub에 이런 게 있음"이라는 낡은 메모**가
남는다. `--prune` 이 그 메모를 지운다. 안 하면 없는 복사본이 계속 보여서 헷갈린다.

## 2. 정말 합쳐졌는지 확인한다

**이 단계를 건너뛰지 않는다.** 합쳐지지 않은 복사본을 지우면 작업이 사라진다.

지금 있는 복사본의 내용이 `origin/main` 안에 들어갔는지 확인한다.

**아직 안 합쳐졌으면** — 정리하지 않고 여기서 끝낸다.

> 아직 안 합쳐졌네요. 규민님이 확인 중이신 것 같습니다.
> 합쳐졌다는 연락을 받으면 그때 다시 `/close-work` 를 쳐주세요.
>
> 기다리는 동안 다른 작업을 시작하셔도 됩니다. 그때는 `/new-work` 부터요.

**이미 `main` 에 있고 지울 복사본이 없으면** — 3단계만 하고 끝낸다.
정리할 게 없는 것은 문제가 아니다. 그렇게 말해준다.

## 3. main 으로 이동하고 최신화

```
git checkout main
```
```
git pull --ff-only origin main
```

`--ff-only` 는 "깔끔하게 이어붙일 수 있을 때만 받아라"는 뜻이다.
꼬인 상태를 조용히 만들지 않는다.

## 4. 다 쓴 복사본 지우기

```
git branch -d <복사본 이름>
```

`-d` 는 **안전 삭제**다. 아직 안 합쳐진 게 남아 있으면 git 이 스스로 거부한다.
강제 삭제(`-D`)는 기본적으로 쓰지 않는다.

### git 이 거부하면

2단계에서 합쳐진 걸 확인했는데도 거부당하는 경우가 있다. 규민이 GitHub에서
**"합치면서 여러 저장 지점을 하나로 합치는 방식"**(squash)으로 합쳤을 때 그렇다.
내용은 들어갔지만 저장 지점의 모양이 달라서 git 이 못 알아본다.

이때는 **내용이 정말 다 들어갔는지 한 번 더 확인한다.** 복사본과 `main` 사이에
남은 차이가 없으면 안전하다.

차이가 없는 것을 확인했으면, **사용자에게 상황을 설명하고 물어본 뒤에만**
강제 삭제를 쓴다. 확인 없이 강제 삭제하지 않는다.

> 내용은 `main` 에 다 들어가 있는데, 합칠 때 저장 지점을 하나로 묶는 방식이라
> git 이 못 알아보고 있어요. 확인해보니 남은 차이는 없습니다.
> 지워도 안전한데, 지울까요?

차이가 남아 있으면 **지우지 않는다.** 무엇이 안 들어갔는지 보여주고 규민에게
물어보라고 안내한다.

## 5. 결과를 확인시켜준다

지웠다고 말만 하지 말고, **내 작업이 진짜로 들어갔는지 눈으로 보여준다.**
개발이 처음인 사람에게는 이 확인이 "한 바퀴를 완주했다"는 실감이 된다.

> 정리 끝났습니다.
>
> - 위진님이 만든 **댓글 삭제 버튼**이 이제 `main` 에 들어가 있습니다
> - 다 쓴 복사본 `feat/comment-delete-button` 은 내 컴퓨터에서도, GitHub에서도 사라졌습니다
> - 지금 `main` 은 팀 최신 상태입니다
>
> 잠시 뒤면 실제 사이트에도 반영됩니다.

## 6. 낡은 복사본이 더 있는지 본다

이번 것 말고도, 예전에 합쳐졌는데 남아 있는 복사본이 있을 수 있다.
찾아서 **보여주고 물어본다. 확인 없이 지우지 않는다.**

> 그런데 예전에 합쳐진 복사본이 아직 남아 있네요:
> - `docs/first-practice-run`
>
> 이미 `main` 에 들어간 것들이라 지워도 아무 영향 없습니다. 지울까요?

지울 게 없으면 이 단계는 조용히 넘어간다. 굳이 "없습니다"라고 말하지 않는다.

## 7. 다음 안내

한 바퀴가 끝났다는 것과, 다음에 무엇부터 하면 되는지 알려준다.

> 이제 깨끗한 상태입니다. 다음 작업을 시작하실 때는
> `/new-work <하려는 작업 한 줄 설명>` 부터 치시면 됩니다.

---

## 하지 않을 것

- **합쳐졌는지 확인하기 전에 복사본을 지우지 않는다.**
- **사용자 확인 없이 강제 삭제하지 않는다.**
- **저장 안 된 변경이 있는데 그냥 진행하지 않는다.**
- 정리할 게 없다고 오류처럼 말하지 않는다. 최신화만 하고 정상적으로 끝낸다.

## 말투 규칙

재환·위진은 개발이 처음이다. 팀 문서(`docs/01-git-기초.md`)의 말을 그대로 쓴다.

| 이 말을 쓴다 | 이 말은 피한다 |
|---|---|
| 내 복사본 | 브랜치 (처음 나올 때만 괄호로 병기) |
| 저장 지점 만들기 | 커밋 |
| GitHub에 올리기 | 푸시 |
| 합쳐달라고 요청하기 | PR 생성 (약어는 괄호로 병기) |

명령어를 알려줄 때는 **한 번에 하나만**, 왜 필요한지 한 줄 설명을 붙인다.
